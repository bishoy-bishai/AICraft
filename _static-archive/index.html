The Problem

Writing code isn't the hard part anymore.

AI can write code. The hard part is making AI write code that belongs in an existing codebase — matching its style, respecting its boundaries, and not quietly making it worse.

WITHOUT DISCIPLINE

Agents invent new patterns next to the old ones, bolt on abstractions nobody asked for, and claim things work without checking.

WITH AICRAFT

Agents learn the codebase first, decide before coding, ship the smallest correct change, and verify before claiming done.

The AICraft Loop

Nine stages, one discipline.

Every change — from a one-line fix to a new feature — moves through the same loop. No stage is optional. Scroll to build it, floor by floor.

The Philosophy

Twelve principles.

Together they form the operating discipline AICraft gives to coding agents.

01

Learn Before You Change

Before writing code, understand how the codebase is structured, how code is written, how responsibilities are divided, how APIs are designed, how data is persisted, how tests are written, and what conventions already exist.

Existing code is the first source of truth.

02

Match the Codebase

AI must learn the project's existing style before generating new code — naming conventions, file organization, architectural patterns, error handling, testing patterns, typing conventions, dependency patterns.

Do not impose your preferred style on an existing project.

Learn the style. Do not blindly copy defects.

03

Understand Before Planning

Before creating tasks or implementation plans, identify the actual requirement, affected areas, existing primitives, ownership boundaries, constraints, dependencies, and risks.

No guessing.

04

Decide Before Coding

Architecture decisions come before implementation. Ask: do we really need a new entity? A new abstraction? Can an existing primitive solve this? Is this capability actually an entity? What's the simplest design that satisfies the requirement?

05

Smallest Correct Change

AICraft prefers the smallest change that correctly solves the problem — not the most sophisticated implementation possible.

No speculative features. No unnecessary abstractions. No unrelated refactoring.

06

Code Should Tell the Story

Good code should make the flow obvious. The reader shouldn't need to understand the entire system to understand one feature.

Request→ Authorization→ Validation→ Business Rule→ Persistence→ Response
07

Every Abstraction Must Earn Its Existence

Before introducing a service, repository, interface, factory, adapter, manager, helper, utility, wrapper, or generic base class — ask what problem it solves today.

If the answer is "future flexibility" — don't add it.

08

Capabilities Are Not Entities

First ask whether a capability can operate over existing primitives, before modeling it as a new one.

✗Search doesn't automatically need a Search entity.
✗Upload doesn't automatically need another knowledge model.
✗Caching doesn't automatically need a Cache entity.
09

Ownership Must Be Explicit

Every responsibility has an owner. Don't let responsibilities leak across boundaries.

10

Testing Is Part of Engineering

A feature isn't complete because the implementation exists. The appropriate behavior must be verified through unit, integration, API, or E2E tests, depending on the feature boundary.

11

Review the Engineering, Not Personal Preference

Reviews should be based on requirements, architecture, correctness, security, data integrity, maintainability, and testing — not "I would have written it differently."

12

AI Must Not Pretend

Evidence over assumption, always.

Ground Rules

The AI must never claim…

  • ✗tests passed when they weren't run
  • ✗an integration works when it wasn't verified
  • ✗a requirement exists when it wasn't specified
  • ✗a file was changed when it wasn't
  • ✗an architecture decision was approved when it wasn't
Evidence over assumption.
